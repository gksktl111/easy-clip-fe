# 버그·오동작: 해결 및 재현 계획

[전체 목록](README.md) · 기준: `dev/e8b47e2` · 1~6번

## 1. 최근 항목 즐겨찾기 버튼

**판단: 코드상 원인 확인, P1.** `src/features/clip/ui/RecentClipsPage.tsx`는 `useClipCollection({ recent: true })`만 호출하고 `onToggleFavorite`을 전달하지 않는다. `hooks/useClipCollection.ts`의 `supportsFavoriteToggle` 기본값은 false다. `ui/ClipItem.tsx`는 버튼을 표시하지만 선택적 콜백만 호출해 클릭이 무반응으로 끝난다. 즐겨찾기 페이지에는 해당 옵션과 이벤트·pending 전달이 이미 있다.

해결안은 최근 페이지에도 동일한 공개 훅 옵션과 이벤트·pending 상태를 연결하는 것이다. mutation 실패가 현재 catch에서 흡수되므로 사용자 오류 피드백도 UI 경계에서 제공한다. 공통 카드의 액션이 없는 경우 표시·비활성 정책을 명시해 같은 누락을 방지한다.

완료 기준: 최근 페이지에서 등록·해제 요청이 각각 한 번 발생하고 표시가 갱신된다. 다른 폴더·즐겨찾기 화면과도 일치하며 연속 클릭·실패 시 기존 값과 재시도 가능 상태가 유지된다. 3페이지 이상 조회한 상태도 포함한다.

## 2. 최하단 폴더를 한 칸 위로 이동

**판단: 추가 재현 필요, P2.** `folder/service/folderCollection.ts`는 마지막 항목의 `up`을 이전 항목의 `before`로 변환할 수 있다. `folder/ui/FolderSidebarContent.tsx`는 드래그한 행의 위·아래 절반을 구분한다. 바로 위 행의 아래쪽에 놓는 것은 원래 위치와 같으므로 의도적으로 무시한다. 보고된 문제가 이 제스처의 기대 차이인지, 메뉴 동작인지, 서버 순서 반영 문제인지는 미확정이다.

`[A,B,C]`에서 메뉴의 C 위 이동은 `{ targetId:C, beforeId:B }`, B 위쪽 드롭은 현재 로직상 `{ targetId:C, afterId:A }`가 된다. 둘 다 `[A,C,B]`가 되어야 한다. 두 폴더만 있을 때, 같은 order 값이 반환될 때, 마지막 행 아래 여백에 놓을 때도 요청·응답·재조회 순서를 기록한다.

해결은 원인에 따라 분리한다. 계산 오류면 삽입 위치 순수 함수를 보완하고, 응답 후 되돌아가면 서버 order 계약을 확인한다. 무효 드롭의 혼동이면 실제 삽입 선과 이동 불가 피드백을 개선한다. mutation optimistic update·rollback은 생명주기 안에 모으는 방향으로 정리한다.

완료 기준: 메뉴·키보드·드래그 모두 인접 위/아래 이동, 첫/끝 경계, 실패 롤백, 새로고침 후 순서 보존을 통과한다. 기존 정렬 테스트는 마지막 항목의 위 이동과 실제 드래그 좌표를 직접 검증하지 않으므로 보강한다. [17번](05-ui-ux.md)과 같은 작업으로 관리한다.

## 3. Pro 카드 버튼 색상

**판단: 대응 코드 존재, 시각 재검증 필요, P2.** `pricing/ui/PricingPlanAction.tsx`는 링크와 버튼 모두 featured 색상을 지정하고, `shared/ui/button/Button.tsx`의 `pricingFeatured`와 `app/globals.css`에 전용 전경·배경·hover 토큰이 있다. 현재 `e2e/pricing.spec.ts`는 언어별 노출과 넘침을 검사하지만 색상 대비를 검증하지 않는다.

비로그인 링크, Free 업그레이드 링크, Pro 현재 플랜 disabled 버튼, 해지 후 재개 버튼을 밝은/어두운 테마에서 확인한다. computed color·background·opacity와 실제 스크린샷을 비교해 전역 스타일, 상속, 배포 CSS 차이 중 원인을 좁힌다. 원인이 확인되면 CTA 토큰과 공통 variant 한 곳에서 수정한다.

완료 기준: 각 상태에서 문구가 읽히고 hover·focus·disabled가 구별된다. 내부 디자인 목표로 일반 본문 대비 4.5:1을 사용하되 이번 검토에서 실제 대비를 측정한 것은 아니다.

## 4. 비로그인 요금제 접근 리다이렉트

**판단: 현재 소스는 공개 접근 허용, P2.** `src/proxy.ts`의 PUBLIC_PATHS에 `/pricing`이 있고 페이지도 `(public)`에 속한다. 보호 레이아웃 밖이므로 현재 코드만으로 랜딩 리다이렉트를 설명할 수 없다. 기존 요금제 E2E도 인증 쿠키 없이 접근하는 시나리오다.

배포 커밋을 먼저 비교하고 직접 URL·랜딩 링크·새로고침에서 HTTP redirect와 클라이언트 router 이동을 구분해 기록한다. 쿠키 없음/유효/만료, 후행 슬래시와 호스트 변경도 분리한다. 구버전이면 최신 배포 반영, 실제 인증 복구 경로가 공개 페이지를 이동시키면 해당 경로만 수정한다.

정책: 요금제 조회는 공개, 결제·구독 변경은 인증 필요. 결제 CTA 클릭 후 로그인한 경우 안전한 내부 복귀 경로를 보존한다. 완료 기준은 인증 상태와 무관하게 `/pricing`에 머물고 결제 진입에서만 인증을 요구하는 것이다. [13번](03-routing.md) 회귀 범위에 포함한다.

## 5. mutation 뒤 기존 조회 클립 유실

**판단: 원인 미확정, P1.** 생성·즐겨찾기·삭제·조회 기록 mutation은 `clipQueryKeys.all`을 invalidate한다. 태그 저장은 `tagQueryCache.ts`에서 기존 pages를 순회해 갱신한다. 검사한 경로에 일괄적으로 첫 페이지만 남기는 코드는 없으므로 invalidate 자체가 유실의 원인이라고 단정하지 않는다.

유실을 서버 데이터 삭제, 재조회 결과에서 제외, 페이지 수 축소, 스크롤 위치 변화, 조건 변경으로 나눠 기록한다. `ClipResultsSection.tsx`는 다음 페이지 요청에 `isFetchingNextPage`만 확인하고 일반 재조회 상태를 전달받지 않아 경합을 검토할 필요가 있다.

해결·완료 기준은 [14·15번 데이터 문서](04-data-state.md)에 단일화한다. 첫 페이지가 꽉 찬 상태에서 새 클립이 앞에 추가되면 같은 페이지 수 재조회 시 마지막 항목이 다음 미조회 페이지로 밀릴 수 있다. 이 경우 실제 삭제와 구분하고, 사용자의 기존 스크롤 위치와 조회 범위를 보존할 제품 정책을 함께 적용한다.

## 6. 설정 재호출과 화면 이동 지연

**판단: 대기 가능한 경로 확인, 배포 인과관계 미확정, P1.** `app/layout.tsx`는 인증 쿠키가 있으면 `getInitialUserSettings()`를 await한다. `settings/server/getInitialUserSettings.ts`는 `cache: no-store`로 서버 API를 호출하며 명시적인 요청 시간 제한이 없다. 클라이언트 `UserSettingsSync.tsx`는 서버 초기화 fallback 때만 실행하고 staleTime은 Infinity다. 따라서 매 이동에서 클라이언트 설정 요청이 반복된다고 단정할 수 없다.

측정안: 같은 origin의 Link 이동, 새 문서 이동, 로그인 콜백, 실제 다른 도메인 이동을 구분한다. 클릭→응답 시작→설정 완료→사용 가능한 화면의 시간을 재고, 서버 요청과 브라우저 요청을 분리한다. 동일 조건에서 여러 번 측정해 p50·p95와 요청 횟수를 남긴다. 인증 정보는 기록하지 않는다.

권고안: 쿠키의 언어·테마로 초기 화면을 구성하고 사용자 설정은 인증 복구 후 한 번 보완하는 방식을 비교 실험한다. 서버 초기화가 필요하면 제한 시간과 fallback을 두고 사용자별 요청 범위 안에서만 중복을 줄인다. 사용자 설정을 공개 전역 캐시에 넣지 않는다. 동일 origin의 앱 이동에서는 Provider를 유지하며 로그인·로그아웃·계정 변경·설정 저장 때 동기화 규칙을 명시한다.

완료 기준: 느리거나 실패하는 설정 API가 화면 진입을 무기한 막지 않는다. 같은 세션의 일반 이동에서 불필요한 클라이언트 설정 재호출이 없고, 언어·테마 깜빡임과 계정 간 설정 혼입이 없다. 성능 수치 목표는 배포 기준선을 측정한 후 확정한다.
