# 클립 조회·mutation·Infinite Query 개선

[전체 목록](README.md) · 기준: `dev/e8b47e2` · 14~15번, 버그 5번의 공통 해결 계획

## 14. 붙여넣기 후 재조회

현재 흐름은 `useFolderClipCapture`의 window paste → 텍스트/이미지 생성 mutation → onSettled에서 전체 clips invalidate다. 생성 실패도 재조회하며 mutation 완료는 invalidation Promise를 기다린다. 페이지 훅이 별도 API 재조회를 수행하는 구조는 아니므로 무조건 “이중 refetch”로 진단하지 않는다.

해결안은 실제 영향이 있는 목록을 서버 성공 응답 이후 갱신하는 것이다. 생성 대상 폴더와 전체 범위 목록을 우선 대상으로 하고 즐겨찾기·최근 목록 포함 여부는 API의 생성/최근 정의에 따른다. 서버가 생성한 항목을 반환해도 검색·정렬 조건을 프론트가 재구현하여 모든 목록에 삽입하지 않는다. 확정되지 않은 저장 결과나 404처럼 재조회가 필요한 오류는 별도 분기한다.

붙여넣기 입력이 search/input/textarea/contenteditable에서 발생하면 클립 생성에서 제외하는 정책을 추가한다. 현재 handler에는 target 검사나 기본 붙여넣기 처리 정책이 명시되어 있지 않다. 같은 이벤트에 이미지와 텍스트가 있으면 현재처럼 이미지 우선으로 한 번 저장하고, 모달·삭제 모드·잠금 폴더에서는 수집을 중단한다.

저장 중 추가 붙여넣기는 현재 처리하지 않는 경로가 있다. 초기 개선안은 무한 대기열 대신 저장 중 안내와 중복 방지를 명시하고, 연속 수집 큐는 별도 요구로 관리하는 것이다. 자동 재시도·중복 제거는 서버의 idempotency 지원 여부를 확인한 후 설계한다.

완료 기준: 일반 텍스트, 이미지, 혼합 clipboard, 검색 입력 중 paste, 저장 중 연속 입력, 4xx·5xx, 페이지 전환, 잠금 발생을 검증한다. 성공 요청 한 번에 불필요한 연쇄 재조회가 발생하지 않고 이미 읽은 목록과 스크롤이 유지되어야 한다.

## 15. Query Cache와 Infinite Query 동기화

### 확인된 구조와 위험 후보

`QueryProvider`는 useState로 QueryClient를 유지한다. `clipQueryKeys.list`는 폴더·즐겨찾기·최근·유형·검색 조건을 포함한다. `useInfiniteClipsQuery`는 pages를 펼쳐 화면 모델로 변환한다. `tagQueryCache`의 태그 갱신은 pageParams와 페이지 메타데이터를 보존한다. 생성·즐겨찾기·삭제·최근 기록은 넓은 invalidate 정책을 사용한다.

공식 가이드상 Infinite Query 재조회는 첫 페이지부터 순차 갱신하며 캐시 제거 시 초기 페이지로 돌아간다. 추가 페이지 조회와 진행 중인 재조회는 같은 캐시 항목을 공유하므로 경합을 피해야 한다. [TanStack Query Infinite Queries](https://github.com/TanStack/query/blob/main/docs/framework/react/guides/infinite-queries.md)를 Context7로 확인했다. 이것만으로 현상 재현이나 원인 확정이 되지는 않는다.

현재 우선 확인할 후보는 다음과 같다.

| 후보 | 코드 근거·관찰 지점 | 확인 방법 |
| --- | --- | --- |
| 재조회와 추가 페이지 요청 경합 | ClipResultsSection은 isFetchingNextPage만 확인 | 느린 refetch 중 sentinel 진입 |
| 새 항목 삽입 후 마지막 항목 밀림 | 같은 페이지 수의 재조회·서버 cursor | 꽉 찬 3페이지에 새 항목 삽입 |
| 다른 조건의 이전 데이터 표시 | placeholderData가 previousData를 그대로 반환 | 폴더/검색 전환 직후 수정 시도 |
| 서버 cursor·정렬 변화 | API 응답 nextCursor·hasMore | 요청 cursor와 반환 ID 순서 비교 |
| 사용자 교체 시 이전 캐시 잔존 | clip/tag 키 자체에는 user ID 없음 | 로그아웃·계정 전환 캐시 정리 추적 |

### 제안 원칙

서버 상태는 Query가 보유하고 별도 Zustand 목록 복사본을 만들지 않는다. 캐시 변환은 feature service, 조회는 queries, mutation 생명주기는 mutations, UI 상태는 hooks에 둔다. 기존 키를 변경한다면 조회·mutation·태그 서비스·테스트를 한 번에 맞춘다.

먼저 일반 재조회 상태까지 하위 UI에 전달하고 fetchNextPage 진입을 제어한다. sentinel은 가시성 토글에만 의존하지 않고 조회 완료 후 추가 페이지가 필요하면 다시 판단하되, 오류 시 자동 무한 재시도가 되지 않게 한다. 조건 변경 중 이전 결과를 표시한다면 다른 폴더 항목에 쓰기 액션을 수행하지 못하도록 placeholder 상태를 전달하거나 범위가 바뀔 때 placeholder를 유지하지 않는다.

캐시 patch는 기존 항목에 대해서만 불변 갱신한다. `pages`, `pageParams`, `nextCursor`, `hasMore`를 보존하며 flat 배열이나 첫 페이지로 캐시를 대체하지 않는다. ID 중복 제거는 표시 보완일 뿐 cursor 오류 해결책이 아니다.

낙관적 갱신이 꼭 필요한 액션만 cancel→snapshot→patch→실패 rollback→정합성 invalidate 순서로 관리한다. 동시 mutation에서 오래된 전체 snapshot이 다른 성공 결과를 되돌리지 않게 대상별 직렬화 또는 항목 단위 복원을 검토한다. 계정 전환 시 캐시 제거가 보장되는지 확인하고 미보장 시 사용자 키 범위 추가와 정리를 함께 적용한다.

### mutation별 정책 초안

| 액션 | 즉시 반영 | 재조회 대상·주의점 |
| --- | --- | --- |
| 클립 생성 | 생성 진행 UI, 성공 표시 | 대상 폴더·관련 전체 목록; 검색 조건에 임의 삽입 금지 |
| 즐겨찾기 | 조회된 해당 ID의 like 상태만 선택적 patch | 즐겨찾기 소속·정렬은 재조회로 확정; 일반 목록에서는 항목 유지 |
| 삭제 | 성공한 ID 제거 가능 | 해당 폴더·최근·즐겨찾기 및 휴지통 갱신 |
| 복사/최근 기록 | 클립보드 성공 피드백과 기록 요청 분리 | recent 목록 우선; 다른 영향은 API 계약 확인 |

| 폴더 이동·삭제 | 제거/이동 결과 반영 | 출발·도착·집계·휴지통, 이동 시 태그 해제 계약 포함 |

### 유실 재현과 완료 기준

1. 페이지마다 다른 ID가 있는 3페이지 이상을 조회하고 화면 ID·Query Key·pages/pageParams·스크롤 기준 항목을 기록한다.
2. 생성·즐겨찾기·삭제·태그 수정·복사 기록을 각각 실행한다. 동시에 다음 페이지 요청, 빠른 검색 변경, 폴더 전환도 실행한다.
3. 서버 응답 ID와 클라이언트 캐시 ID를 비교한다. 서버가 더 이상 반환하지 않는 항목과 프론트만 잃은 항목을 분리한다. 테스트 데이터만 기록한다.
4. 느린 응답 순서 역전, 실패, 재시도, 계정 교체를 추가한다. 유실 재현 테스트를 먼저 고정하고 수정 후 통과시킨다.

정렬이 변하지 않는 속성 수정은 기존 항목·순서·조회 페이지를 유지한다. 생성처럼 앞쪽 삽입으로 항목이 밀리는 경우에는 사용자가 보고 있던 기준 ID와 위치를 보존하고 필요하면 추가 페이지를 읽어 기존 조회 범위를 복원하는 정책을 권고한다. 서버에서 삭제·권한 회수된 항목은 보존 대상에서 제외한다.

검색어·폴더 변경은 새 Query Key에서 시작하고 이전 cursor를 재사용하지 않는다. 배경 재조회 중 전체 목록을 빈 화면/스켈레톤으로 바꾸지 않으며 실패 시 마지막 성공 데이터를 유지하고 재시도를 제공한다. pages와 pageParams 길이는 항상 일치해야 한다.

기존 단위 테스트는 옵션과 태그 cache patch를 일부 확인하지만 다중 페이지·동시 요청 회귀를 충분히 증명하지 못한다. 단위 테스트에는 불변성·메타데이터 보존을, Playwright에는 3페이지 데이터와 응답 지연·순서 제어를 추가한다. 실제 서버 cursor 계약은 mock 테스트와 별도로 검증한다.
