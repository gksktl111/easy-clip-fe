# 다국어 호출과 클립·폴더 도메인 구조 검토

[전체 목록](README.md) · 기준: `dev/e8b47e2` · 18~19번

## 18. 각 컴포넌트의 다국어 훅 호출

**판단:** UI마다 `useTranslations`를 호출하는 것 자체는 결함이 아니다. `ClipItem`, `FilterBar`, `ClipCollectionPage`는 각자의 표시 문구를 가진다. `FolderSidebarContent`는 일부 문구를 하위 표현 컴포넌트에 props로 전달한다. 두 방식을 무조건 하나로 통일하기보다 컴포넌트 책임에 맞게 선택한다.

| 영역 | 권고 |
| --- | --- |
| feature UI | 자기 namespace 문구를 직접 조회 |
| 도메인 비종속 shared UI | label·children·설명 props를 받아 재사용 |
| API·service·query cache | 번역 훅 없이 오류 코드·타입·순수 결과 반환 |
| 페이지 조합 훅 | 오류를 UI/feedback 경계로 전달, 요청 로직과 문구 결합 최소화 |
| 서버 전용 UI | 필요 시 서버 번역 API 사용, 클라이언트 경계 확장을 피함 |

`useFolderClipCapture.ts`의 저장 실패 문구와 이미지 검증 오류 같은 하드코딩을 먼저 메시지 키로 옮기는 것이 실질적인 개선이다. `FilterBar`처럼 namespace 두 개를 읽는 코드도 의미가 다르면 유지한다. 모든 문구를 페이지에서 주입하면 props가 커지고 독립성이 줄어들 수 있으므로 번역 호출 횟수만 줄이는 리팩터링은 권고하지 않는다.

번역 함수와 숫자·날짜 포맷팅을 구분하며 로케일 변경 후 memo된 문구가 남지 않도록 의존성을 검토한다. 오류 코드는 타입으로 정의하고 사용자 문구는 네 로케일에 함께 추가한다. 작은 컴포넌트에 namespace를 지정해 호출하는 패턴은 [next-intl 공식 문서](https://next-intl.dev/docs/usage/translations)와 부합한다. 위 책임 표는 프로젝트의 설계 제안이다.

완료 기준: 사용자 노출 하드코딩 제거, 메시지 키 누락 없음, 런타임 로케일 전환 반영, 순수 서비스에서 React/번역 의존 없음. 성능 개선을 주장하려면 실제 렌더링 측정을 별도로 수행한다.

## 19. 클립과 폴더 도메인을 합칠지 검토

**권고: 별도 feature 유지.** 폴더는 컨테이너의 생성·이름·순서·삭제를, 클립은 수집·조회·복사·즐겨찾기·태그를 소유한다. 사용자 경험에서 함께 보여도 API와 변경 생명주기가 다르다. 현재 `app/(protected)/(workspace)`가 조합 지점을 제공하고 각 feature에 공개 entrypoint가 있다.

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| clip·folder 완전 통합 | 일부 교차 import 감소 | 큰 feature, 태그·구독·휴지통까지 책임 확대 가능 | 현재 근거로는 비권고 |
| 별도 feature + app 조합 | 기존 책임·공개 API 유지 | 협력 계약을 명시해야 함 | 권고 |
| workspace feature 신설 | 조합 책임 집중 | app 역할 중복·이동 비용 | 조합 로직이 여러 곳에서 반복될 때 재검토 |

당장 도메인 폴더를 옮기지 않고 `app → features → shared` 방향을 유지한다. 폴더 삭제·이동이 클립 목록·태그·휴지통에 영향을 주는 경로는 최소 공개 함수/타입으로 협력하거나 app에서 이벤트를 연결한다. 도메인 결합을 숨기려고 folderId 정책이나 클립 캐시를 shared로 옮기지 않는다.

태그는 폴더 범위를 가지지만 클립 분류 UI와 결합되어 현재 clip 안에 있다. 폴더 기능이라는 이름만으로 이동하지 않는다. 향후 독립 태그 관리 요구가 커지면 소유권과 API 경계를 다시 결정한다. URL의 folder 선택자도 라우팅 조합 계약이며 두 도메인 통합의 근거가 되지 않는다.

실행안: 공개 import와 순환 의존을 점검하고 [15번](04-data-state.md)의 캐시 service 책임부터 정리한다. `useFolderActions`의 요청·optimistic 생명주기처럼 기존 규칙과 다른 부분은 해당 기능 수정 시 단계적으로 옮긴다. 도메인 통합은 같은 데이터와 변경 정책을 지속적으로 중복 소유한다는 증거가 생길 때 재검토한다.

완료 기준: 순환·역방향 의존을 늘리지 않고 폴더 생성·정렬·삭제와 클립 생성·태그·즐겨찾기를 독립적으로 검증할 수 있다. 구조 변경이 공개 API·라우팅·DTO의 불필요한 변경을 유발하지 않아야 한다.
