# Easy Clip 포트폴리오 적합성 검토

> 작성일: 2026-08-26
>
> 범위: 프론트엔드 저장소의 코드, 설정, CI, 테스트, 문서 및 로컬 검증 결과
>
> 전제: 백엔드의 보안·데이터 모델·운영 환경과 실제 배포 UI는 이 검토 범위에 포함하지 않는다.

## 최종 판단

**포트폴리오로 사용할 수는 있지만, 현재 상태만으로 대표작으로 내세우기에는 설득력이 부족하다.**

코드에서는 실제 제품에 가까운 기능과 중급 이상의 프론트엔드 구현력을 확인할 수 있다. 그러나 처음 보는 평가자가 제품의 핵심 흐름을 체험하고, 기술적 판단과 본인의 기여를 짧은 시간 안에 이해할 수 있는 자료가 부족하다.

따라서 현재 적합성은 다음과 같이 판단한다.

| 용도                 | 판단         | 이유                                                                      |
| -------------------- | ------------ | ------------------------------------------------------------------------- |
| 보조 포트폴리오      | 사용 가능    | 기능 범위와 코드 구조가 단순 클론보다 깊다.                               |
| 대표 포트폴리오      | 보완 후 권장 | README, 데모, 핵심 E2E, Next.js 활용 근거가 더 필요하다.                  |
| 실서비스 완성품 주장 | 근거 부족    | 핵심 사용자 흐름·배포 품질·백엔드 연동을 이 저장소만으로 증명하기 어렵다. |

| ------------------ | ---: | ----------------------------------------------------------------------------------------------------- |
| 기능·도메인 복잡도 | 7/10 | OAuth 기반 인증, 폴더·클립, 즐겨찾기·최근·휴지통, 구독 결제, 테마, 다국어를 다룬다.                   |

| 테스트 신뢰도      | 5/10 | 단위 테스트는 있으나 핵심 인증·클립·폴더 사용자 흐름의 E2E 증거가 부족하다.                           |
| 포트폴리오 전달력  | 3/10 | README에 제품 설명, 데모, 본인 기여, 스크린샷, 아키텍처 서사가 없다.                                  |

점수는 채용 판단을 대체하는 절대값이 아니라, 이 저장소를 처음 본 기술 평가자가 얻을 수 있는 증거의 양을 기준으로 한 상대 평가다.

## 강점

### 제품 기능의 깊이

다음은 단순 화면 구현보다 높은 평가를 받을 수 있는 요소다.

- httpOnly cookie 기반 세션 복구, 401 처리, refresh 요청 병합
- 클립 생성·삭제·즐겨찾기·무한 스크롤과 TanStack Query 캐시 무효화
- 폴더 생성·이름 변경·정렬·삭제와 optimistic UI
- 최근 조회·즐겨찾기·휴지통 복원/영구 삭제 흐름
- Toss Payments 기반 구독 진입 및 결과 화면
- 다크 모드, 다국어, 반응형 사이드바, 접근성 속성
- 공통 UI와 디자인 토큰을 Storybook으로 문서화

이 조합은 "React로 화면을 만들 수 있다"보다 "상태, 실패, 사용자 흐름, 외부 시스템 연동을 고려해 기능을 만들 수 있다"는 신호를 준다.

### 코드베이스의 기본 체력

- feature별 `api`, `model`, `queries`, `mutations`, `hooks`, `ui` 책임이 비교적 구분돼 있다.
- `server-only` 모듈과 공개 환경변수 검증이 존재한다.
- TypeScript strict 설정, ESLint, Vitest, Playwright, Storybook, GitHub Actions CI가 준비돼 있다.
- `.env*`, 테스트 산출물, build 결과가 `.gitignore`에 포함되어 있다.

### 검증 결과

검토 시점에 다음 항목은 통과했다.

| 명령                      | 결과                       |
| ------------------------- | -------------------------- |
| `npm run lint`            | 통과                       |
| `npm run typecheck`       | 통과                       |
| `npm run test`            | 7개 파일, 24개 테스트 통과 |
| `npm run build`           | 통과                       |
| `npm run build-storybook` | 통과                       |

CI도 lint, 타입 검사, build, 단위 테스트, E2E 테스트를 순서대로 수행하도록 구성되어 있다. 자세한 내용은 `.github/workflows/ci.yml`을 참고한다.

## 대표작으로는 아직 부족한 이유

### 1. README가 포트폴리오의 첫 관문 역할을 하지 못한다

현재 `README.md`는 설치·환경변수·명령어·Swagger 링크 중심이다. 저장소를 처음 본 사람은 다음 질문에 답을 얻기 어렵다.

- Easy Clip이 해결하는 문제와 핵심 사용자 시나리오는 무엇인가?
- 어떤 기능이 실제로 구현되었는가?
- 프론트엔드와 백엔드는 어떻게 나뉘며, 본인이 맡은 범위는 어디까지인가?
- 사용 기술을 왜 선택했는가?
- 실제 동작은 어디에서 볼 수 있는가?
- 인증이 필요한 핵심 기능은 어떻게 체험하는가?

이 문제는 코드 품질보다 포트폴리오 평가에 더 큰 영향을 줄 수 있다. 채용 담당자나 면접관은 보통 README와 데모에서 흥미를 느낀 뒤 코드로 들어간다.

### 2. 핵심 기능을 검증하거나 체험할 경로가 약하다

현재 E2E는 랜딩 페이지 1건과 요금제 다국어/가로 넘침 4건이다. 즉 아래 핵심 흐름은 자동화된 사용자 시나리오로 증명되지 않는다.

- 로그인 이후 세션 복구 및 보호 route 진입
- 폴더 생성·정렬·삭제와 route 이동
- 텍스트/이미지 클립 생성, 검색, 즐겨찾기, 복사
- 선택 삭제와 휴지통 복원·영구 삭제
- 결제 성공/실패 및 구독 상태 전환

외부 API와 OAuth가 필요한 프로젝트라면 공개 demo 계정, 안전한 mock API 모드, 시드 데이터, 또는 1~2분의 제품 walkthrough 영상 중 하나는 반드시 제공하는 편이 좋다.

### 3. Next.js를 쓰는 이유가 코드에서 충분히 보이지 않는다

`npm run build` 결과 모든 App Router route가 `ƒ`(요청 시 동적 렌더링)로 나온다. 또한 보호 화면의 실질적인 데이터 흐름은 대체로 다음과 같다.

```text
클라이언트 hydration
  → SessionProvider의 세션 복구
  → AuthGuard
  → React Query의 폴더/클립/휴지통 조회
```

이는 잘못된 구현은 아니지만, Next.js의 핵심 장점인 서버 최초 데이터 준비, 클라이언트 JavaScript 절감, 경로 params의 서버 검증, streaming과 route-level loading UI를 활용하지 못한 구조다.

상세 분석과 단계적 전환안은 [NEXTJS_ARCHITECTURE_ANALYSIS.md](./NEXTJS_ARCHITECTURE_ANALYSIS.md)에 정리되어 있다. 포트폴리오에서 Next.js를 기술 선택으로 강조하려면, 최소한 폴더 상세 화면 하나는 서버에서 첫 목록을 조회하고 React Query cache를 hydrate하는 구조로 전환하는 것을 권장한다.

### 4. 다국어 지원의 마감 품질이 일관되지 않다

`ko`, `en`, `ja`, `zh` 메시지 파일과 요금제 locale E2E가 있다. 반면 세션 오류, 클립 저장 오류, 결제 결과, 앱 셸 등에는 한국어 하드코딩 문구가 남아 있다.

다국어를 포트폴리오 장점으로 제시하려면 사용자에게 노출되는 문구를 모두 메시지로 옮기고, 최소 한 개의 핵심 인증 후 화면을 각 언어로 검증해야 한다.

### 5. 사용자 경험의 경로 단위 안전망이 부족하다

`src/app`에 `loading.tsx`, `error.tsx`, `not-found.tsx`가 없다. client query 수준의 loading/error UI는 존재하지만, 동적 route 전환과 예상하지 못한 segment 오류를 다루는 App Router 경계는 없다.

포트폴리오에서는 성공 화면만큼 실패·빈 상태·권한 없음·잘못된 URL을 처리하는 방식을 보여주는 것이 중요하다.

### 6. 핵심 제품 주장의 시연 근거가 필요하다

랜딩은 기기 간 동기화를 핵심 가치로 제시한다. 그러나 이 프론트엔드 저장소만으로는 동기화 방식, 백엔드의 역할, 브라우저 확장 기능 유무, 실제 기기 간 동작을 충분히 판단할 수 없다.

이 기능이 제품의 차별점이라면 다음을 README나 데모 영상에 포함한다.

- 시스템 구성도와 데이터 흐름
- 두 기기 또는 두 브라우저 세션에서 동기화되는 실제 화면
- 지원 범위와 제약(브라우저 권한, clipboard 동작, 동기화 시점)

## 포트폴리오 공개 전 우선순위

### 반드시 할 일

1. README를 포트폴리오용으로 다시 작성한다.
   - 제품 한 줄 소개와 문제 정의
   - 라이브 데모/배포 URL, 스크린샷 또는 GIF
   - 핵심 기능 목록과 사용자 흐름
   - 기술 스택과 기술 선택 이유
   - 프론트엔드·백엔드·외부 결제의 역할 분리
   - 본인 기여와 어려웠던 문제, 해결 방식
   - 로컬 실행 및 데모 계정/mock 방법
2. 핵심 E2E를 최소 3개 추가한다.
   - 인증 후 폴더 생성 → 클립 생성 → 검색/즐겨찾기
   - 클립 삭제 → 휴지통 복원
   - 폴더 삭제 → 목록/route/cache 갱신
3. 다국어 하드코딩 문구를 정리하고, 핵심 화면 하나를 네 locale로 확인한다.

### 대표작 수준으로 끌어올릴 일

1. 보호 폴더 route의 첫 데이터 조회를 서버로 이동하고 React Query hydrate를 구현한다.
2. `loading.tsx`, `error.tsx`, `not-found.tsx`를 추가해 경로 단위 실패 UX를 완성한다.
3. 공개 화면의 metadata, noindex 정책, 정적/동적 렌더링 전략을 명시한다.
4. 실제 성능 측정 결과(초기 요청 수, LCP 등)를 전후 비교로 남긴다.
5. 아키텍처 의사결정 기록을 README에서 링크한다.

## 포트폴리오에서의 권장 서술 방식

현재 상태에서 이 프로젝트를 소개한다면 "완성된 상용 서비스"보다 아래와 같이 정확하게 표현하는 편이 좋다.

> 여러 기기에서 재사용할 텍스트·이미지·색상 클립을 폴더 단위로 관리하는 웹 애플리케이션입니다. OAuth 세션 복구, TanStack Query 기반 서버 상태와 캐시 무효화, 무한 스크롤, 휴지통 복원, Toss Payments 구독 흐름, 다국어·테마 UI를 구현했습니다. 현재는 App Router의 서버 최초 데이터 조회 구조로 점진 전환 중입니다.

이 표현은 구현한 내용을 과장하지 않으면서도, 현재의 기술적 고민과 개선 방향을 보여준다.

## 검토 한계와 재검증 필요 항목

- Chrome DevTools 연결이 실행 환경에서 종료되어 실제 렌더링 화면과 Lighthouse 결과는 확보하지 못했다.
- 로컬 Playwright 실행은 Chromium의 시스템 라이브러리 `libnspr4.so` 부재로 실패했다. 이는 애플리케이션 테스트 실패가 아니라 현재 실행 환경 문제다.
- CI에는 `npx playwright install --with-deps chromium` 단계가 있으므로, 실제 GitHub Actions 실행 결과를 확인해야 E2E 성공을 최종 주장할 수 있다.
- 백엔드 API, 인증 cookie 정책, 결제 승인 보안, 실제 배포 환경은 별도 저장소/환경 검토가 필요하다.
